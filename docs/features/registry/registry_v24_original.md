## 0. 결론 요약

**기술적으로 가능하다. 단 "가능"의 난이도가 대상 유형에 따라 3단계로 갈린다.**

핵심 근거는 아키텍처에 있다. 현재 엔진에서 Claude가 실제로 보는 것은 DOM이 아니라 **워커가 만들어 준 JSON 요소 목록**이다:

```json
{"ref":"a12","role":"button","name":"+ New Company","tag":"button","value":"","testId":"add-company","href":null,"type":null}
```

`ACTION_SYSTEM`/`JUDGE_SYSTEM` 프롬프트(`agent-worker/src/agent.js:221`, `:239`)는 이 스키마만 소비한다. **같은 모양의 JSON을 네이티브 UI 트리에서 만들어낼 수 있다면, 그 위의 대부분(액션 결정·판정·Job 도메인·TestResult 기록·프론트 UI)이 그대로 재사용된다.** Android UiAutomator2 / iOS XCUITest의 페이지 소스는 이 매핑이 거의 1:1로 성립한다(§4).

> ⚠️ **"수정 없이"는 아니다** (리뷰 A-1 수용). 실행 루프 `runTestCase`/`agenticGoal` 안에 **`page.url()`이 9곳**(`agent.js:191, 265, 283, 286, 290, 322, 347, 355, 365`) 남아 있고, 네이티브 앱에는 URL이라는 개념 자체가 없다. 재사용되는 것은 **루프의 구조와 프롬프트**이지 파일이 아니다. 실제 수정 범위는 §2 표를 참조.

| 대상 유형 | 가능성 | 필요 작업 | 예상 규모 |
|-----------|:---:|-----------|-----------|
| **(a) 모바일 웹 / PWA** | ✅ 지금도 거의 됨 | Playwright device emulation 3~5줄 + 실행 프로파일 필드 1개 | 1~2일 (§13) |
| **(b) 하이브리드 / WebView 앱** | ✅ 가능 | Appium 세션 + WebView 컨텍스트 스위칭 → 웹 스냅샷 코드 재사용 | (c)에 부수 |
| **(c) 네이티브 앱 (Android/iOS)** | ⭕ 가능하나 신규 드라이버 필요 | Driver 추상화 + Appium 드라이버 구현 + 인프라 분리 | Phase 0 PoC 후 산정 |
| **(d) Flutter / Unity 등 자체 렌더 앱** | ⚠️ 별도 트랙 | 접근성 트리 미노출 → 계측 빌드 또는 비전 기반 | 본 문서 범위 밖 (§3) |

**가장 큰 제약은 코드가 아니라 인프라다.** iOS는 XCUITest가 Xcode를 요구해 **macOS에서만** 구동되고, Android 에뮬레이터는 KVM(하드웨어 가속)이 필요해 **현재 프로드 EC2(t3.small, Linux)에 지금의 `agent-worker` 컨테이너로 얹을 수 없다.** 모바일 워커는 별도 런타임으로 분리 배치해야 한다(§7).

## 0-1. 확정 스코프 (2026-08-24, User 결정)

| 항목 | 결정 |
|------|------|
| 대상 앱 | **패스오더** (카페 미리주문 앱, App Store `id1350702018`, 운영사 페이타랩) |
| 플랫폼 | **iOS + Android 둘 다** (2026-08-24 재결정 — 아래 참조) |
| 우선순위 (**제품**) | **① iOS·Android 테스트 자동화 → ② 실행 화면을 웹에서 보기 → ③ 백그라운드 전환** |
| 우선순위 (**수요일 데모**) | **iOS 우선** (User 결정, 2026-08-24). Android는 **폴백 겸 Xcode 대기시간 활용** — 먼저 동작시켜 두되 **데모 목표는 iOS**다. 드라이버는 속성 매핑 스위치만 갈아끼우면 되는 구조라(Step 2) 어느 쪽을 세워도 나머지가 따라온다 |
| 데드라인 | **2026-08-26(수) 면접 데모** (오늘 포함 2일) — 전체 완성이 아니라 §10의 데모 최소선까지 |

> **왜 목표는 iOS이면서 착수는 Android가 먼저인가** — 이건 모순이 아니라 **목표와 순서를 분리**한 것이다.
>
> - **목표가 iOS인 이유**(User 결정): 대상 앱 패스오더를 **실기기에서** 검증한다는 서사가 가장 강하고, 시뮬레이터에 설치할 수 없어(§iOS 제3자 앱 제약) 실기기 검증이 곧 iOS 검증이다.
> - **착수가 Android가 먼저인 이유**: Xcode 10~15GB 다운로드·설치가 **물리적으로 몇 시간**이라, 그 대기시간에 iOS 작업을 시작할 방법이 없다. 그 창에 Android를 세워두면 ① 매핑 스크립트·프롬프트·판정 규칙을 **미리 검증**해두고(iOS는 속성 분기만 추가) ② **폴백이 손에 들어온다.**
>
> ⚠️ **감수하는 리스크**(2차 리뷰 S-1에서 지적한 것 — 결정이 바뀌었으므로 리스크로 남긴다): 2일에 툴체인 2벌을 세우는데 iOS 쪽 크리티컬 패스에 **WDA 서명**이 있다. 공식 문서가 "a bit of a headache"라 적는 작업이고, 무료 Apple ID면 번들 ID 제약 + 7일 만료가 붙는다. **여기서 막히면 iOS 데모는 성립하지 않는다.**
>
> → 그래서 **폴백 발동 시각을 미리 못박는다**: Step 0-I1(WDA 서명)이 **화요일 22시까지 안 뚫리면** 더 쓰지 않고 ① 시뮬레이터 + iOS 기본 앱, 그것도 안 되면 ② 이미 세워둔 Android로 간다. "막히면 전환"은 시각을 안 정하면 안 지켜진다(§12-2).
>
> 면접 서사는 어느 쪽이든 손해가 아니다 — 폴백으로 가더라도 "**드라이버의 속성 매핑만 갈아끼우면 두 플랫폼이 같은 엔진으로 돈다**"는 설계 자체가 보여줄 것이다.

> **실행 모드는 기능 2개가 아니라 축 1개다.** "보여주기"와 "백그라운드"는 같은 스위치의 양 끝이라, 한쪽을 만들면 다른 쪽은 사실상 공짜다. 다만 Playwright는 `launch({headless})`가 **launch 시점에 고정**되어 실행 중 전환이 불가능하므로, 진짜 런타임 전환을 하려면 headless를 아예 쓰지 않는 설계가 필요하다(§9-4).

> **요구 ②·③의 적용 대상은 모바일이 아니라 실행 대상 전부다** — **웹(Playwright) · Android · iOS 셋 모두**에 적용된다. 특히 **웹이 가장 시급하다**: 모바일은 최소한 에뮬레이터 창이나 기기 화면이라도 눈앞에 있지만, 현재 웹 워커는 **Docker 안에서 headless로 돌아 아무 데서도 볼 수 없다.** v22가 "브라우저 화면이 안 보인다"를 첫 번째 문제로 지목한 그 상태 그대로다. 즉 ②는 모바일에 얹는 부가 기능이 아니라 **기존 웹 실행의 미해결 과제를 함께 푸는 일**이다.

### Android 포함 결정 (2026-08-24 재결정)

당초 "안드로이드 기기가 없어서" 제외했으나 **그 근거는 성립하지 않는다**(리뷰 D-1). Android는 실기기 없이 **에뮬레이터로 충분**하고, iOS 시뮬레이터와 달리 **Play Store 앱을 그대로 설치할 수 있다.** iOS 최대 리스크인 WDA 서명 문제도 없고, 설치 용량도 Xcode(10~15GB)보다 가볍다.

**코드 관점에서 Android 추가는 거의 공짜다:**
- Appium 서버와 webdriverio 클라이언트가 **동일**하다. 드라이버만 `appium driver install uiautomator2`로 하나 더 깐다
- §4의 속성 매핑표가 **이미 Android/iOS 양쪽을 다 담고 있다**. `drivers/mobile.js` 한 파일에서 플랫폼 스위치로 `class/text/content-desc/resource-id` ↔ `type/label/name/accessibilityIdentifier`만 갈라주면 된다
- Driver 추상화(Step 1)와 프롬프트·판정·Job 도메인은 **완전히 공유**된다
- → iOS를 끝낸 뒤 Android는 **추가 30~40% 수준**이지, 두 배가 아니다

**요구 ②·③의 성립 범위** (§9-5-1에서 백그라운드를 **가역**으로 확정한 뒤 갱신)

| 대상 | ② 화면 보기 | ③ 백그라운드 = **뷰어 접기(가역)** | (참고) 리소스 절약형 "조용히 실행" = 비가역 |
|------|:---:|:---:|:---:|
| 웹 | ✅ Xvfb + noVNC / 스크린샷 | ✅ | ✅ `headless` 기동 |
| **Android 에뮬레이터** | ✅ 에뮬레이터 창 · 스크린샷 스트림 | ✅ | ✅ **`emulator -no-window` 기동** |
| iOS 시뮬레이터 | ✅ `simctl` 캡처 | ✅ | ❌ GUI 세션 필요 |
| iOS 실기기 | ✅ 기기 화면 (QuickTime 미러링) | ✅ (단, 기기 화면 자체는 계속 켜져 있다) | ❌ 화면이 항상 켜져 있어야 함 |

> **정정 (3차 리뷰)**: 이전 판은 *"요구 ③은 Android에서만 온전히 성립한다"*를 Android 포함의 **가장 강한 이유**로 들었다. 그러나 §9-5-1에서 백그라운드를 "뷰어를 접는 것"으로 정의하면서 **③은 웹·Android·iOS 셋 모두에서 성립**하게 됐다. 따라서 그 논거는 **더 이상 유효하지 않다.**
>
> Android를 포함하는 이유는 이제 두 가지로 정리된다:
> 1. **서명 절차가 없어 수요일 데모를 보장할 수 있다** (가장 강한 이유 — §0-1 우선순위 행)
> 2. 리소스 절약형 "조용히 실행"(`-no-window`)이 iOS에서는 불가하지만 Android에서는 가능하다 — 다만 이건 **당장 필요한 기능이 아니다**(§9-5-1 주석)

**단, 비용이 0은 아니다 — 툴체인은 2벌이다:**
- iOS: Xcode(10~15GB) + WDA 서명 + 실기기
- Android: Android SDK + 에뮬레이터 이미지(3~6GB, Apple Silicon은 ARM64 이미지로 하드웨어 가속)
- 설치·검증이 각각 필요하므로 **환경 세팅 시간은 대략 2배**다. 코드가 싼 것이지 세팅이 싼 게 아니다

> ⚠️ **Android의 고유 리스크 — 패스오더가 에뮬레이터에서 안 뜰 수 있다.** 결제가 걸린 앱은 **Play Integrity / 에뮬레이터·루팅 탐지**로 실행 자체를 거부하는 경우가 흔하다. 그러면 Android도 실기기가 필요해지는데 보유 기기가 없다. → **Step 0-A1에서 30분 안에 먼저 확인**하고, 막히면 Android 데모 대상만 다른 앱(에뮬레이터 기본 앱 등)으로 바꾼다. "네이티브 앱 자동화가 된다"는 명제는 그대로 증명된다.

**설치 순서 권고**: 데모 목표는 iOS지만 **가장 먼저 하는 일은 Xcode 다운로드를 거는 것**이다(몇 시간). 그 대기창에서 Android를 세워 매핑 스크립트·프롬프트를 미리 검증하고 폴백을 확보한다 — **iOS를 뒤로 미루는 게 아니라, iOS를 시작할 수 없는 시간을 쓰는 것**이다. Xcode가 준비되는 즉시 iOS 트랙(Step 0-I1)으로 넘어간다.

### iOS 제3자 앱의 결정적 제약 2가지

1. **시뮬레이터에는 패스오더를 설치할 수 없다.** App Store IPA는 실기기 ARM 바이너리 + FairPlay 암호화라, 시뮬레이터 슬라이스 빌드를 요구하는 시뮬레이터에서는 원리적으로 실행되지 않는다. → **실기기 iPhone + USB 연결이 필수**다.
   > ✅ **확보됨** (User 확인, 2026-08-24): 본인 iPhone + **USB-C ↔ Lightning 케이블**로 MacBook에 연결 가능. iOS 우선 결정의 최대 전제가 해결됐다 — 남은 iOS 리스크는 **WDA 서명 하나**로 좁혀진다.
   > 커넥터가 Lightning이면 iPhone 14 이하이므로 iOS 16+ 가정이 유효하다 → **개발자 모드 + UI 자동화 토글**이 필요하다(Step 0-I1).
2. **WebDriverAgent 서명이 필요하다.** XCUITest 드라이버는 `WebDriverAgent-Runner`라는 헬퍼 앱을 기기에 설치하고 **그걸 통해** 대상 앱을 자동화한다. Apple Developer 계정으로 서명해야 하며, 무료 Apple ID도 가능하지만 **번들 ID 제약**(Xcode가 이미 승인한 ID만) + **7일 만료**가 붙는다. 공식 문서도 코드 서명을 "a bit of a headache"라고 적고 있다. → **수요일 데모의 최대 리스크 지점.**

### 폴백 (리스크 대응)

**"네이티브 앱을 AI가 자연어 TC로 조작·판정한다"는 명제는 대상 앱이 무엇이든 동일하게 증명된다.** 데모 가치의 손실이 크지 않으므로 폴백을 부끄러워할 이유가 없다. 플랫폼별 폴백 경로:

데모 목표인 iOS부터, 막히는 순서대로 내려간다.

| # | 막히는 지점 | 폴백 | 발동 기준 |
|:---:|---|---|---|
| 1 | **iOS 실기기 — WDA 서명이 안 뚫린다** (최대 리스크) | **iOS 시뮬레이터 + iOS 기본 앱**(설정·연락처). 시뮬레이터는 WDA 서명 문제가 없어 훨씬 안전하다. 패스오더는 설치 불가하므로 대상 앱이 바뀐다 | Step 0-I1이 **화요일 22시** 초과 시 즉시 |
| 2 | **패스오더가 Flutter라 트리가 안 보인다** | 대상 앱만 교체(iOS 기본 앱 또는 네이티브로 확인된 다른 앱). "네이티브 앱 자동화" 명제는 그대로 증명된다 | Step 0-I3 트리 덤프 즉시 |
| 3 | **iOS가 전부 막힌다** | **이미 세워둔 Android로 간다** — 그래서 Android를 먼저 동작시켜 두는 것이다 | 수요일 오전까지 iOS 미완 |
| 4 | **Android도 패스오더가 에뮬레이터에서 차단**(Play Integrity) | 에뮬레이터 기본 앱 또는 탐지가 없는 다른 앱으로 대상만 교체 | Step 0-A1의 **30분 관문** 초과 시 즉시 |

### 패스오더 프레임워크 미확인 리스크

**Flutter로 만들어졌다면 접근성 트리가 병합/부재라 판정이 불가능**해진다(§1-d). 웹 검색으로는 스택이 확인되지 않았고, **가장 빠른 확인법은 Appium을 띄운 뒤 트리를 한 번 덤프하는 것(5분)**이다. Phase 0의 첫 관문으로 배치했다(Step 0-A2 / 0-I3).

### ⚠️ 안전 규칙 (필수)

패스오더는 **실제 주문과 결제가 일어나는 상용 서비스**다. 에이전트가 자유롭게 클릭하다 실주문이 발생하면 실제로 돈이 나간다. v21의 "외부 제품 읽기 전용 안전선"은 **미구현 상태**이므로 코드가 막아주지 않는다.

**사전 예방 (사고를 안 나게)**
- ✅ 데모 TC는 **읽기 전용으로만** 구성한다 — 매장 검색, 매장 상세 진입, 메뉴 조회, 카테고리 이동
- ❌ **장바구니 담기 이후 단계·결제 화면 접근 금지**
- ✅ 실행 전 앱에서 **결제 수단을 해제**해두면 이중 안전장치가 된다
- ✅ 로그인은 **카카오 / Apple / 이메일** 중 택1이며(실측, §17) 외부 인증이 끼어 에이전트가 자율 수행하기 어렵다 → **사람이 미리 로그인**한 상태에서 시작 (§6-D의 "사전 로그인 상태 재사용"과 같은 원리)
- ⚠️ **단, 사전 로그인은 v20 B2-1 사고의 재현 조건이다**(리뷰 C-3 수용). 당시 `exec_seed_note`가 이미 끝난 로그인을 또 시켜 액션 예산(`MAX_STEP_ACTIONS`)을 전부 소진하고 TC 본문은 시작도 못 했다. **seedNote에 "이미 로그인된 상태다. 추가 로그인 시도 금지"를 명시**하고 로그인 관련 지시는 한 줄도 넣지 않는다

**사후 차단 (사고가 나는 중에 멈추기) — 리뷰 B-2 수용, 최우선**

위 항목은 전부 "사고를 미리 막는" 수단일 뿐, **사고가 진행 중일 때 멈추는 수단이 지금 전혀 없다.** 코드로 확인한 현 상태:

| 계층 | 현 상태 | 근거 |
|------|---------|------|
| 프론트 | **중지 버튼이 없다.** `닫기`/`×`는 `onClose`만 호출 — 모달만 닫히고 워커는 계속 돈다 | `AgentRunModal.tsx:106-111, 200-207` |
| 백엔드 | `cancelJob`은 **DB 상태만 CANCELLED로 바꾼다.** 워커에 전달되는 신호가 없다 | `AgentExecutionServiceImpl:78-86` |
| 워커 | TC 목록을 **끝까지 순회한다.** 중간에 job 상태를 다시 확인하지 않는다 | `index.js:78-90` |

→ **상용 결제 앱을 사람이 못 멈추는 상태로 자동화하는 것은 받아들일 수 없다.** 데모 전 필수 구현으로 격상한다(Step 1-K):
- 워커: 각 TC 실행 **전**, 그리고 각 step 실행 **전**에 job 상태를 조회해 `CANCELLED`면 즉시 중단한다. **완료 보고는 하지 않는다** — `cancelJob`이 이미 `status`·`completedAt`을 종료 상태로 만들었고(`:83-84`), `completeJob`은 **DONE/FAILED만 허용**하므로(`:157-160`) `complete(CANCELLED)`는 예외를 던지고 그 예외가 `index.js:97`의 `complete(FAILED)`로 흘러가 **CANCELLED를 FAILED로 덮어쓴다**(2차 리뷰 N-1). → 워커에 전용 `CancelledError`를 두고 `runJob`의 catch에서 이것만 별도 분기해 **아무 보고 없이 return**한다
- 프론트: `AgentRunModal`에 **[중지]** 버튼 → `POST /{jobId}/cancel`
- 물리적 최후 수단: **에뮬레이터 종료 / iPhone USB 케이블 분리** — 데모 중 실제로 쓸 수 있게 미리 리허설해둘 것

## 1. 질문을 정확한 형태로 쪼개기

"앱도 지원하고 싶다"는 요구는 실제로 서로 다른 4개의 기술 문제다. 어느 것을 원하는지에 따라 답이 완전히 달라진다.

| # | 유형 | 실체 | 관측 수단 |
|---|------|------|-----------|
| a | 모바일 웹 / PWA | 그냥 웹. 뷰포트와 UA만 다름 | 현재 DOM 스냅샷 그대로 |
| b | 하이브리드 (Cordova/Capacitor, WebView 화면) | 네이티브 껍데기 + 내부는 웹 | 컨텍스트 전환 후 DOM |
| c | 네이티브 (Kotlin/Swift, React Native) | OS 위젯 트리 | UiAutomator2 / XCUITest 접근성 트리 |
| d | 자체 렌더 (Flutter/Impeller, Unity, 게임) | 캔버스에 픽셀을 직접 그림 | 접근성 트리 부실 → 계측 or 비전 |

React Native는 (c)에 속한다 — RN은 실제 네이티브 위젯을 그리므로 트리가 정상적으로 노출되고, `testID`가 Android `resource-id` / iOS `accessibilityIdentifier`로 그대로 내려간다. 우리 스냅샷의 `testId` 필드와 정확히 대응한다(§4).

Flutter는 (d)다. 플랫폼의 네이티브 뷰 계층을 우회해 자체 엔진으로 픽셀을 그리기 때문에 표준 Appium 셀렉터가 위젯을 아예 못 보는 경우가 많고, 노출되는 semantics 트리도 여러 위젯을 하나의 노드로 병합해 개별 타게팅이 불가능해지는 문제가 알려져 있다. `appium-flutter-driver`는 Dart VM Service Protocol을 쓰며 커뮤니티 유지보수이고, 앱 측 계측을 요구한다 → **외부 제품 대상으로는 사실상 불가**, 자기 제품이라도 별도 트랙이다.

실제 코드를 층으로 갈라보면 **웹 전용은 관측·액션·로그인 3개 층뿐**이고, 나머지는 전부 플랫폼 무관이다.

| 층 | 파일 | 웹 결합도 | 판정 |
|----|------|:---:|------|
| Job 도메인 (스키마·상태머신·카운터) | `AgentExecutionJobEntity/ResultEntity`, `AgentExecutionServiceImpl` | 없음 | ♻️ 그대로 |
| Job API (`/api/agent-executions` 생성·claim·record·complete) | `AgentExecutionController` | 없음 | ♻️ 그대로 |

### 이식의 seam — 왜 이게 좋은 소식인가

교체 대상 6개는 전부 **"페이지를 관측해서 JSON을 만들고, JSON 속 ref로 액션을 실행한다"**는 하나의 인터페이스 뒤에 있다. v20이 만들어 둔 이 경계 덕분에, 모바일 지원은 **엔진 재작성이 아니라 드라이버 1개 추가 + 루프의 좁은 보정**으로 성립한다.

**`page.url()` 9곳 처리 방안**: 드라이버 계약에 `location()`을 추가해 "현재 위치를 사람이 읽을 수 있는 한 줄"로 추상화한다 — 웹은 URL 그대로, iOS는 **최상위 화면 식별자**(활성 앱 bundleId + 네비게이션 타이틀 또는 최상단 `XCUIElementTypeNavigationBar`의 name)를 반환한다. 호출부 9곳을 `driver.location()`으로 바꾸면 루프 로직과 프롬프트는 손대지 않아도 된다. 부수 효과로 `stepLogs.observed`가 iOS에서도 의미 있는 값을 갖게 된다(리뷰 E-2 연계).

역으로, v20이 실전에서 얻은 교훈(B2-1~B2-7)의 대부분은 **드라이버가 아니라 프롬프트·판정 규칙에 축적**되어 있어 모바일에서도 그대로 유효하다:
- B2-2 "같은 이름 요소 구분" → 모바일에선 `resource-id`/`accessibilityIdentifier`로 더 쉽게 해결
- B2-5 "컨테이너 이름에 자식 텍스트가 섞임" → 네이티브 컨테이너에서도 **똑같이 발생**(§4 주의)
- B2-6 "ref 재할당으로 같은 버튼 재클릭" → 모바일은 ref가 더 불안정해 **더 심해짐**(§4)
- B2-7 "CSS/diff가 필요한 expected는 판정 불가" → 모바일에서도 동일한 TC 작성 규칙 적용

| 후보 | 앱 소스 수정 | Node에서 제어 | 트리 관측 품질 | iOS | 외부 앱(제3자 APK/IPA) | 평가 |
|------|:---:|:---:|:---:|:---:|:---:|------|
| **Appium 3 (UiAutomator2 + XCUITest)** | 불필요 | ✅ webdriverio | 상 (속성 풍부) | ✅ (macOS 필요) | ✅ | **권고** |

### 선택: Appium 3 + webdriverio

**이유**
1. **앱 소스 수정이 필요 없다** — v21의 "외부 제품 지원" 방향과 정합. Detox/Espresso는 이 조건에서 탈락.
2. **Node에서 완전히 프로그래밍 가능** — 현 워커가 Node ESM이라 런타임 추가 없이 붙는다.
3. **관측 속성이 우리 스키마와 대응한다**(§4).
4. **디바이스 팜이 전부 Appium 엔드포인트를 표준으로 제공** — 로컬 PoC → 클라우드 실기기로 코드 변경 없이(드라이버 URL·capabilities만) 승급 가능(§7).

**주의할 버전 사실 (2026-08 기준)**
- Appium 3가 정식이며, UiAutomator2 드라이버 5.0.0부터는 **Appium 3에서만 호환**된다.
- Appium 3의 Node 요구 범위는 **`^20.19.0 || ^22.12.0 || >=24.0.0`** 이다 — 단순한 "20.19 이상"이 아니라 **21.x와 22.0~22.11이 미지원 구간**이다(npm은 10+). 현 워커는 `engines.node >=20`, Playwright 이미지가 Node 20이므로 **패치 버전 확인이 필수**다: 20.19 미만이면 베이스 이미지 상향, 22를 쓸 거면 22.12 이상이어야 한다.
- Appium 3에서 일부 레거시 엔드포인트가 제거되고 보안 플래그 접두사(`uiautomator2:adb_shell` 등)가 강제된다. webdriverio는 v9.27.0(2026-03)에서 Appium 3 호환 수정이 반영됐다 → **webdriverio 9.27+ 고정** 권장.
- v20에서 `playwright`를 `1.47.2`로 **정확 고정**해 도커 이미지 브라우저 revision 불일치를 해결한 전례가 있다(v20 "Phase 2 런타임 검증" 1번). 동일 원칙으로 `webdriverio`/드라이버 버전도 캐럿(`^`) 금지, 정확 고정할 것.

## 4. 관측 스키마 매핑 — 실현 가능성의 핵심

현재 스냅샷이 만드는 필드가 네이티브 트리에서 무엇으로 오는지의 대응표. **이게 성립하면 프롬프트를 안 고쳐도 된다.**

| 우리 필드 | Android (UiAutomator2 page source) | iOS (XCUITest page source) | 비고 |
|-----------|-----------------------------------|---------------------------|------|
| `ref` | ❌ 주입 불가 | ❌ 주입 불가 | **구조 변경 필요** — 아래 참조 |
| `role` | `class` (`android.widget.Button`) → 축약 | `type` (`XCUIElementTypeButton`) → 축약 | 접두사 제거해 `button`/`edittext` 등으로 정규화 |
| `name` | `text` ‖ `content-desc` | `label` ‖ `name` | 웹의 `aria-label`/텍스트와 동일 역할 |
| `tag` | `class` 원문 | `type` 원문 | 그대로 |
| `value` | EditText의 `text` | `value` | 그대로 |
| `testId` | `resource-id` | `accessibilityIdentifier` | **RN `testID`가 여기로 내려옴** |
| `href` | (없음) | (없음) | null. 딥링크가 유사 개념이나 요소 속성은 아님 |
| `type` | `class` 세분 | `elementType` | 축약 매핑 |
| **`clickable`** (신규) | `clickable="true"` | `enabled` + type | **웹엔 없던 명시 신호** |
| **`enabled`** (신규) | `enabled` | `enabled` | disabled 요소 클릭 낭비 방지 (B2-6 재발 억제) |
| **`displayed`** (신규) | `displayed` | `visible` | 화면 밖 요소 필터 |
| **`scrollable`** (신규) | `scrollable="true"` | — | 스크롤 컨테이너 식별 |
| **`bounds`** (신규) | `bounds="[x,y][x,y]"` | `rect` | 비전 폴백·순서 정렬용 |

### 웹보다 **좋아지는** 부분

v20 B2-4에서 우리는 `<div onClick>`으로 구현된 카드가 스냅샷에 안 잡히는 문제를 **CSS `cursor` 값 휴리스틱**이라는 불완전한 우회로 해결했다("100% 커버는 아님"이라고 문서가 명시). 네이티브 트리는 **`clickable="true"`를 프레임워크가 직접 선언**하므로 이 휴리스틱 자체가 불필요해진다. 관측 신뢰성은 이 지점에서 오히려 올라간다.

### 웹보다 **나빠지는** 부분 (3가지, 전부 대응 설계 필요)

1. **`ref` 주입이 불가능하다.** 웹에선 `el.setAttribute('data-agent-ref', ref)`로 요소에 표식을 박고 나중에 `[data-agent-ref="a12"]`로 되찾았다(`agent.js:69`, `:252`). 네이티브 트리에는 임의 속성을 쓸 수 없다.
   → **대응**: 워커 메모리에 `ref → locator` 맵을 유지한다. locator 우선순위는 `accessibility id` → `resource-id`(Android) → 절대 xpath(최후). 단 **xpath는 트리가 조금만 변해도 깨지므로**, 액션 실행 시 실패하면 **직전 스냅샷의 name/testId로 재조회**하는 폴백을 반드시 둔다. B2-6("ref가 스냅샷마다 재할당되어 같은 버튼을 또 클릭")이 모바일에서 더 자주 재현될 구조이므로, 이미 프롬프트에 넣어둔 "previousActions에 같은 name의 성공 click이 있으면 done" 규칙이 여기서 더 중요해진다.

2. **화면 밖 요소가 트리에 없다.** Android `RecyclerView`/iOS `UITableView`는 가상화되어 **보이는 셀만** 트리에 존재한다. "생성한 항목이 목록에 추가됨" 같은 우리 표준 expected는 **스크롤 없이 판정 불가**다.
   → **대응**: ① 액션 어휘에 `scroll` 추가(§5), ② `JUDGE_SYSTEM`에 "목록 존재 확인 시 보이는 범위에 없으면 FAIL이 아니라 스크롤 필요"를 명시하고 판정 전 자동 스크롤 탐색 1~2회를 허용, ③ TC 작성 가이드(`docs/qa/testcase_guideline.md`)에 모바일 항목 추가.

3. **`pageText` 대응물이 빈약하다.** 웹의 `document.body.innerText`는 화면의 모든 텍스트를 한 번에 준다. 네이티브에선 트리 노드의 `text`/`label`을 순회 수집해 합성해야 하며, **역시 보이는 범위로 한정**된다. v20 B2-7에서 `pageText` 절단(1500→6000자)이 오판정을 유발했던 전례가 있으므로, 합성 로직과 상한을 초기부터 실측할 것.

## 5. 액션 스키마 확장

현재 어휘: `click | fill | select | navigate | done` (`agent.js:224`).

| 액션 | 웹 (현재) | 모바일 매핑 | 조치 |
|------|-----------|-------------|------|
| `click` | `locator.click()` | `element.click()` | 그대로 |
| `fill` | `locator.fill()` | `element.setValue()` (+ `clearValue`) | 그대로 |
| `select` | `selectOption()` (**웹은 필수 — 아래 참조**) | **대응물 없음** — 네이티브 picker/spinner는 "클릭 → 리스트에서 선택"의 2단계 | 웹 유지 / **모바일 미지원 처리** |
| `navigate` | `page.goto(url)` | **딥링크**(`mobile: deepLink`) 또는 액티비티 시작 | 의미 재정의 |
| `done` | — | — | 그대로 |
| **`back`** (신규) | 브라우저 뒤로가기 | Android 하드웨어 back / iOS 네비 바 back | 추가 필요 |
| **`scroll`** (신규) | (거의 불필요) | **필수** — §4-2 | 추가 필요 |
| **`swipe`** (신규) | — | 캐러셀/스와이프 삭제 등 | 선택 |
| **`longPress`** (신규) | — | 컨텍스트 메뉴 | 선택 |
| **`hideKeyboard`** (신규) | — | 키보드가 대상 요소를 가림 (모바일 특유 실패 모드) | 권장 |

### `select` 처리 — 리뷰 D-3 부분 반박

리뷰는 "`select`를 확장하지 말고 **아예 제거**하고 클릭 2번으로 대체하면 웹/모바일 공용 코드를 유지할 수 있다"고 제안했다. **모바일 쪽 결론은 맞지만, 웹에서 제거하면 깨진다.**

HTML `<select>`의 드롭다운은 **브라우저가 OS 위젯으로 그리는 것이라 DOM에 옵션이 노출되지 않는다.** Playwright에서 select를 클릭해 열어도 그 안의 항목을 클릭할 수단이 없고, 그래서 `selectOption()`이라는 전용 API가 존재한다. 실제로 v20 B2-7에서 `JUDGE_SYSTEM`에 "select 값 확인은 elements의 value만으로 충분"이라는 규칙까지 추가했을 만큼 my-atlas TC에서 활발히 쓰이는 액션이다. 제거하면 웹 회귀가 난다.

**확정**: 액션 어휘에서 `select`를 **유지**하되, **모바일 드라이버에서는 지원하지 않는다**(호출 시 "이 플랫폼에는 select가 없다. 클릭으로 열고 항목을 클릭하라"는 오류를 반환해 에이전트가 다음 액션에서 스스로 우회하게 한다 — 실패 액션을 history에 남겨 재시도를 유도하는 기존 패턴과 동일). 프롬프트는 **단일 유지**하고, 드라이버가 제공하는 액션 목록을 입력 JSON에 실어 보내 모델이 쓸 수 있는 것만 쓰게 한다. 프롬프트를 플랫폼별로 분기하지 않으므로 유지보수 부담이 늘지 않는다.

> **부수 비용**(2차 리뷰 S-2): 미지원 오류를 history에 남겨 우회시키는 설계는 `MAX_STEP_ACTIONS`(기본 4)를 **1회 소모**한다. select가 필요한 모바일 TC는 실질 예산이 3으로 줄어든다 → **모바일 프로파일에서 `MAX_STEP_ACTIONS`를 5~6으로 올리는 것**을 함께 검토한다.

`scroll`/`back` 추가는 `ACTION_SYSTEM` 문구 수정을 수반한다.

## 6. 로그인 / 시드 상태 — 웹보다 명백히 어렵다

현재 웹은 `autoLogin`(`agent.js:152`)이 **in-page `fetch`로 로그인 API를 호출하고 토큰을 `localStorage`에 주입**하는 결정적 fast-path를 쓴다. v20 Phase 2 런타임 검증 5번에서 폼 입력(`fill`)이 React controlled-input을 놓쳐 로그인이 불안정했기 때문에 의도적으로 택한 방식이다.

**네이티브 앱에는 이런 in-process 훅이 없다.** 후보:

| 방식 | 결정성 | 적용 범위 | 비고 |
|------|:---:|-----------|------|
| A. 딥링크 + 토큰 파라미터 | 상 | 자기 제품(테스트 빌드) | 가장 깔끔. 앱 측 지원 필요 |
| B. `adb shell`로 SharedPreferences/파일 주입 | 상 | Android + 디버그 빌드 | Appium 3에선 `uiautomator2:adb_shell` 보안 플래그 필요 |
| C. **에이전트 폼 로그인** (관측→입력→제출) | 중 | **범용, 외부 앱 포함** | v21 Step 3과 동일 과제 |
| D. **사전 로그인된 에뮬레이터 스냅샷 재사용** | 상 | Android 에뮬레이터 | **PoC에 가장 실용적** — AVD 스냅샷을 로그인 상태로 저장 후 매 실행 복원 |

→ **PoC는 D, 제품화는 A(자기 제품) + C(외부 앱) 병행**을 권고한다.

> **v21과의 강결합**: 자격증명을 Product별로 안전하게 저장하는 문제(v21 Step 1~3)는 모바일에서도 **똑같이, 그리고 더 일찍** 필요하다. 워커 env 하나(`AGENT_WORKER_USERNAME/PASSWORD`)로 고정된 현 구조로는 모바일 대상 제품을 추가할 수 없다. **v21을 선행하거나 최소한 자격증명 스키마만이라도 함께 설계**해야 v24가 실질적으로 착수 가능하다.

## 7. 인프라 — 실제로 가장 큰 제약

### 현 배치로는 안 된다

`agent-worker`는 `mcr.microsoft.com/playwright:v1.47.2-jammy`(Linux) 컨테이너로 `docker-compose.yml`의 `worker` 프로파일에 얹혀 돈다. 여기에 모바일을 그대로 추가할 수 없다:

- **Android 에뮬레이터는 KVM(하드웨어 가속)이 필요**하다. 중첩 가상화를 호스트 VM이 지원해야 하는데 대부분의 클라우드 CI/일반 인스턴스가 이를 제공하지 않는다. **t3.small에서는 불가**(v20이 이미 "t3.small 메모리에서 Chromium 구동 위험"을 확인 필요 항목으로 남겨둔 것과 같은 계열의 문제이며, 에뮬레이터는 그보다 훨씬 무겁다).
- **iOS는 macOS에서만 가능하다.** XCUITest는 Xcode 툴체인을 요구하므로 Linux 컨테이너에서 원리적으로 구동 불가.

### 실행 위치 후보

| 위치 | Android | iOS | 상시성 | 비용 | 평가 |
|------|:---:|:---:|:---:|------|------|
| **로컬 Mac (현 개발기)** | ✅ (ARM64 에뮬레이터 가속) | ✅ (시뮬레이터) | ❌ 개발자 머신 | 0 | **PoC 최적** — v20 Phase 0도 로컬 워커(안 C)로 시작했다 |
| Linux 서버 + 에뮬레이터 | △ (KVM 되는 metal/전용 인스턴스 필요) | ❌ | ✅ | 높음 (metal 인스턴스) | 비용 대비 부적절 |
| GitHub Actions | ✅ (larger Linux runner에서 하드웨어 가속 Android 가상화 지원, KVM udev 권한 설정 필요) | ✅ (macOS 러너, 비쌈) | △ (러너 기동 지연) | 중 | v20이 검토했던 "안 B"와 동일 논리 — 인터랙티브성 낮음 |
| **디바이스 팜 (BrowserStack / AWS Device Farm / LambdaTest)** | ✅ 실기기 | ✅ 실기기 | ✅ | AWS DF: $0.17/device-min 또는 $250/슬롯·월 · BrowserStack App Automate: 공개가 기준 월 $199~249 (2026-08 시점, 실계약 시 재확인) | **제품화 시 최유력** — 코드 변경 없이 드라이버 URL·capabilities만 교체 |

### 권고 배치

```
[backend / Job API]  ← 변경 없음
        ↑ 폴링 (claim/context/recordResult/complete)
        │
        ├── agent-worker (web)     : 현행 유지 — Linux 컨테이너
        └── agent-worker-mobile    : 신규 — 별도 런타임
                                      PoC     → 로컬 Mac + 에뮬레이터/시뮬레이터
                                      제품화  → 디바이스 팜 (Appium 원격 엔드포인트)
```

워커가 **백엔드를 폴링하는 구조**(v20 Step 2에서 큐 대신 폴링을 택함)라는 점이 여기서 결정적으로 유리하다. 워커가 어디서 돌든 백엔드에 인바운드 연결만 되면 되므로, **모바일 워커를 로컬 Mac에 두고 백엔드의 Job을 집어가게 하는 배치가 아키텍처 변경 없이 성립한다.** 단 `POLL_PRODUCT_ID`로 Product를 고정하는 현 방식은 워커가 2종이 되면 부족하므로, **Job에 실행 대상 종류를 실어 워커가 자기 담당만 집어가게 하는 필터**가 필요하다(§9).

## 8. 성능·비용 — 실측이 필요한 1순위 숫자

현재로선 **추정**이며, PoC의 핵심 측정 목표다.

| 항목 | 웹 (현재 실측 기반) | 모바일 (추정) | 근거 |
|------|---------------------|---------------|------|
| 스냅샷 1회 지연 | `page.evaluate` — 수십 ms | **수백 ms ~ 수 초** | Appium `getPageSource`는 XCUITest에서 특히 느리다는 이슈가 공개 트래커에 보고되어 있음 |
| TC당 스냅샷 횟수 | step당 최대 `MAX_STEP_ACTIONS`(4) + 판정 1 + `snapshotStable` 재시도 | 동일 | `agent.js:318`, `:342` |
| TC당 wall-clock | v20 PoC 기준 1분40초 ~ 6분40초 | **웹의 2~5배 추정** | 위 두 항목의 곱 |
| 토큰 | Haiku 기준, TC당 수천~수만 | 필터링 전이면 **급증**, 필터 후엔 유사 | 네이티브 XML은 레이아웃 컨테이너가 매우 많음 → `clickable/displayed` 필터 + depth 제한 필수 (웹의 `simplifyAxNode` `maxDepth=15`와 같은 처리) |

**따라서 PoC에서 반드시 숫자로 남길 것**: ① 스냅샷 1회 지연(Android/iOS 각각), ② 필터 전후 트리 노드 수와 토큰, ③ TC당 wall-clock, ④ 스크롤이 필요한 판정의 실패율.

> v20 PoC가 "정밀 토큰/$ 측정은 metered 워커 필요 → Phase E로 이연"하고 아직 안 한 상태다. 모바일은 이 숫자가 go/no-go를 좌우하므로 **이연하지 말 것**.

## 9. 권고 아키텍처

### 9-1. 워커: Driver 인터페이스 도입

`agent.js`에서 드라이버 의존 부분만 뽑아 인터페이스 뒤로 보낸다. **`runTestCase`의 루프 구조(step 순회 → 액션 결정 → 실행 → 판정)와 프롬프트는 유지한다.** 단 §2에서 짚었듯 `page.url()` 9곳은 `driver.location()`으로 치환해야 하므로 **파일이 무변경인 것은 아니다**(Step 3).

```
agent-worker/src/
  index.js            # 오케스트레이션 — 변경 최소 (드라이버 선택 분기만)
  agent.js            # runTestCase / askJson / 프롬프트 — 드라이버 무관으로 정리
  drivers/
    driver.js         # 인터페이스 계약(JSDoc) + 공통 유틸
    web.js            # 현행 Playwright 구현 이관 (동작 무변경)
    mobile.js         # 신규 — Appium(webdriverio)
```

```js
/**
 * UiDriver 계약 — runTestCase는 이 인터페이스만 안다.
 *   start(profile)        세션 시작 (브라우저 launch | Appium 세션 생성)
 *   enter(target)         대상 진입 (baseUrl goto | 앱 실행/딥링크)
 *   snapshot()            → [{ref, role, name, tag, value, testId, clickable, enabled, ...}]
 *   text()                → 화면의 보이는 텍스트
 *   tree()                → 계층 구조 (a11y 트리 | 네이티브 트리 요약)
 *   execute(action)       click|fill|navigate|back|scroll|... 실행 + 안정화 대기
 *   screenshot()          → Buffer  (v22 증적과 접점)
 *   close()
 */
```

**리팩터 안전판**: `web.js` 이관은 **동작이 1비트도 바뀌면 안 된다.** 이관 직후 기존 gold TC(992/999/1006/1007/1009 — v20 B2에서 전부 PASS 확인됨)를 재실행해 동일 verdict가 나오는지로 회귀를 검증한다.

### 9-2. 백엔드: 실행 프로파일 확장 (초안)

현재 `product`의 실행 프로파일은 `exec_base_url`, `exec_seed_note` 두 개뿐이고, `WorkerContextResponse`도 `baseUrl`/`seedNote`만 싣는다(`AgentExecutionServiceImpl:191`). 여기에 대상 종류를 추가한다.

```
product (마이그레이션 V{YYYYMMDD}{HHmm}__add_mobile_exec_profile.sql)
  exec_target_kind      WEB | MOBILE_WEB | ANDROID | IOS      -- 신규, default WEB (기존 데이터 호환)
  exec_app_id           앱 패키지명(Android) / 번들 ID(iOS)     -- 신규
  exec_app_artifact     APK/IPA 경로 또는 URL (설치 필요 시)     -- 신규
  exec_device_name      에뮬레이터/디바이스 이름                -- 신규
  exec_platform_version OS 버전                                -- 신규
  exec_driver_url       Appium 서버 URL (로컬 or 디바이스 팜)    -- 신규
  exec_base_url         (기존 — MOBILE_WEB에서도 계속 사용)
  exec_seed_note        (기존 — 그대로)
```

- `product.platform`(`Platform` enum: `WEB/DESKTOP/MOBILE/ETC`)이 **이미 존재**하지만 이건 제품의 분류 메타데이터이고, 실행 방식은 별개다(같은 제품이 웹과 앱을 둘 다 가질 수 있다). **재사용하지 말고 `exec_target_kind`를 신설**할 것.
- `WorkerContextResponse`에 `execTarget` 객체를 추가한다. 기존 `baseUrl`/`seedNote` 필드는 **유지**해야 현재 워커가 안 깨진다(무중단 전환).
- 워커 필터: `GET /api/agent-executions?productId=` 기반 폴링에 **대상 종류 필터**를 추가하거나, 워커가 context를 받은 뒤 자기 담당이 아니면 claim을 반납하는 경로가 필요하다. 전자 권고.

`ExecProfileModal`에 `exec_target_kind` 셀렉트를 두고 종류에 따라 입력 필드를 전환한다(드릴다운 규칙 유지 — 패널 병렬 배치 금지).

### 9-4. 실행 모드 — 보여주기 / 백그라운드

**전제**: 두 요구는 하나의 축이다(§0-1). 그리고 Playwright의 `launch({headless})`가 launch 시점 고정이라, **실행 중 headed↔headless 전환은 브라우저 재시작 = TC 상태 소실**을 뜻한다. 따라서 진짜 런타임 전환을 원하면 **headless를 아예 쓰지 않는 쪽**으로 설계해야 한다.

**2-B 상세 설계 — 항상 headed + 가상 디스플레이 + noVNC 중계**

> 아래는 **2-B의 설계이며 착수는 2-A 이후다**(이 절 끝의 「2단계로 쪼갠다」 참조).

```
워커 컨테이너
  Xvfb (:99)                     ← 가상 디스플레이 (화면 없는 서버에서도 headed 구동)
    └ Chromium (headed, DISPLAY=:99)
  x11vnc → websockify/noVNC → :6080
                ↑
  my-atlas 프론트 AgentRunModal 안
    <iframe src="…/vnc.html?autoconnect=1&view_only=1">
```

- **보여주기** = 모달에서 뷰어를 연다
- **백그라운드** = 뷰어를 닫는다 (실행은 그대로 계속)
- → **런타임 전환이 구조적으로 성립**하고, 로컬 창이 아니라 **웹 UI 안에서** 보이므로 원격·다른 기기에서도 관전 가능
- `view_only=1` — 관전 전용. 사람이 실수로 클릭해 에이전트 실행을 방해하지 못하게 막는다
- v22가 "라이브 스트리밍은 범위 밖 — trace/screenshot으로 대체"로 제외했던 항목을 **되살리는 결정**이다. v22의 스크린샷 증적과는 상호 배타가 아니라 보완 관계(실시간 관전 + 사후 증적)

**이 축은 플랫폼마다 다르게 동작한다 (중요)**

| 대상 | ② 보여주기 | ③ 백그라운드 (뷰어 접기) | 구현 수단 |
|------|---|---|---|
| **웹 (Playwright)** — *현재 Docker headless라 관전 수단 0* | ✅ | ✅ | 보기: Xvfb + x11vnc + noVNC 또는 스크린샷 스트림 · 백그라운드: 뷰어 접기 |
| **Android 에뮬레이터** | ✅ | ✅ | 보기: 에뮬레이터 창 / `scrcpy` / `adb exec-out screencap` 스트림 · 백그라운드: 뷰어 접기 |
| iOS 시뮬레이터 | ✅ | ✅ | `simctl` 화면 캡처 · 백그라운드: 뷰어 접기 |
| iOS 실기기 | ✅ | ✅ | QuickTime USB 미러링(코드 0줄) · 백그라운드: 뷰어 접기 (**기기 화면 자체는 계속 켜져 있다**) |

→ **③을 "뷰어를 접는 것"으로 정의하면 네 조합 전부에서 성립한다**(§9-5-1). 워커는 계속 그리고 있고 사용자가 안 볼 뿐이므로 **가역**이다.

→ 따라서 모드 토글은 **어떤 대상에서도 비활성화하지 않는다.** 이전 판은 "iOS 실기기는 ③이 불가하므로 비활성화 + 사유 툴팁"으로 두었으나(리뷰 E-4), **가역 정의에서는 그 제약 자체가 사라진다.** E-4의 원칙("조건에 따라 UI 요소가 사라지면 혼란스럽다")은 그대로 유효하고, 이제는 아예 숨길 일도 비활성화할 일도 없다.

> **다만 iOS 실기기는 안내가 필요하다.** 뷰어를 접어도 아이폰 화면은 계속 켜진 채 조작된다. 백그라운드 전환 시 보조 문구로 *"기기 화면에서는 계속 실행됩니다"*를 표시한다 — 컨펌창이 아니라 **안내**다.

> **설계 함의**: `screenshot()` 기반 2-A는 **웹·Android·iOS 전부에서 동일하게 동작하는 유일한 수단**이다. 2-B(Xvfb+noVNC)는 **웹 전용**이다.
>
> ⚠️ **정정 (3차 리뷰 M-1)**: 이전 판은 *"2-B가 웹 브라우저와 Android 에뮬레이터를 둘 다 커버한다 — 에뮬레이터도 X11 GUI 앱이라 같은 가상 디스플레이에 렌더되므로"*라고 적었으나 **성립하지 않는다.**
> 1. **§7의 배치와 모순된다.** §7은 에뮬레이터가 KVM을 요구해 Linux 워커 컨테이너에 못 얹힌다고 못박고, 모바일 워커를 **로컬 Mac**에 둔다.
> 2. **macOS에는 X11이 없다.** Mac에서 Android 에뮬레이터는 네이티브 Cocoa 앱으로 뜨며 X 서버에 렌더하지 않는다.
> 3. 웹 워커(Docker Linux)와 모바일 워커(로컬 Mac)는 **다른 머신의 다른 프로세스**다. 가상 디스플레이 하나를 공유할 수 없다.
>
> 또한 `-gpu swiftshader_indirect`는 **소프트웨어 렌더링** 플래그라, Apple Silicon에서 켜면 §0-1이 강조한 ARM64 하드웨어 가속을 스스로 버리게 된다.
>
> → **Android의 고품질 실시간 관전은 [`scrcpy`](https://github.com/genymobile/scrcpy)로 간다.** adb 기반이라 X11이 필요 없고 macOS에서 동작하며 30~60fps가 나온다. Xvfb 경로와는 별개 수단이다.

**플랫폼별 관전 수단 정리**

| 대상 | 2-A (스크린샷) | 고품질 실시간 |
|------|:---:|---|
| 웹 (Docker Linux) | ✅ | **2-B** — Xvfb + x11vnc + noVNC |
| Android (로컬 Mac) | ✅ | **scrcpy** (adb 미러링) 또는 에뮬레이터 창 |
| iOS 실기기 | ✅ | QuickTime USB 미러링 |

#### 2단계로 쪼갠다 (리뷰 D-2 부분 수용)

리뷰는 "Xvfb + VNC는 과설계다. 이미 2초 폴링이 있으니 **step마다 스크린샷 한 장씩 실어 보내면** 인프라 없이 거의 실시간 효과를 낸다"고 지적했다. **부분적으로 맞다.** 그리고 더 강한 논거가 하나 더 있다 — **Xvfb/noVNC는 Docker Linux 워커에서만 성립**하므로(위 설계 함의), 로컬 Mac에서 도는 **Android·iOS 어느 쪽도 커버하지 못한다.** 스크린샷 방식만이 **웹·Android·iOS 셋 모두에서 동일하게 동작하는 유일한 수단**이다.

다만 스크린샷 폴링에는 상한이 있다. **폴링 주기 자체는 상수 하나이므로**(`AgentRunModal.tsx:16` `POLL_INTERVAL_MS = 2000`) 스크린샷 전용 경로를 300~500ms로 낮추면 **초당 2~3프레임**까지는 올라간다 — 즉 "2초라서 안 된다"는 근거는 성립하지 않는다(2차 리뷰 S-3). 그 이상의 부드러움이나 DOM 상호작용 관전이 캡처 방식으로 불가능할 뿐이다.

→ **2-B의 정당화는 "초당 10프레임 이상 + DOM 관전"이다.** 그 요구가 없다면 2-A에서 멈춰도 된다. 그래서 둘 다 하되 순서를 나눈다:

| 단계 | 방식 | 적용 | 비용 | 성격 |
|------|------|------|------|------|
| **2-A** | step별 스크린샷을 기존 폴링 응답에 실어 표시 | **웹 · Android · iOS 전부** | 0.5~1일 | 먼저 출시. v22 Step 1~2와 사실상 동일 작업이라 **중복 투자가 아니다** |
| **2-B** | Xvfb + x11vnc + noVNC iframe | **웹 전용** (Docker Linux). Android는 scrcpy, iOS는 2-A로 | 2~3일 | 진짜 실시간. 2-A 위에 얹는다 |

2-A만으로도 "백그라운드 전환"은 성립한다(뷰어를 안 보면 됨). 2-B는 부드러움을 위한 상위 옵션이다.

> **웹이 2-B의 최대 수혜자다.** 모바일은 로컬에서 에뮬레이터 창·기기 화면을 직접 볼 수라도 있지만, Docker 안 headless 브라우저는 2-B 없이는 **웹 UI에서 볼 방법이 아예 없다.** 요구 ②를 "모바일 기능"으로 읽으면 정작 가장 안 보이는 대상을 놓치게 된다.

**보안 (리뷰 지적 반영)**: noVNC 엔드포인트는 인증 없이 열면 **실행 중인 브라우저를 아무나 조작**할 수 있다. `view_only=1`은 클라이언트 측 설정이라 방어가 아니다. 2-B 착수 시 ① 백엔드가 발급하는 **1회용 토큰**을 websockify 앞단에서 검증, ② 포트를 외부에 직접 노출하지 않고 백엔드 리버스 프록시 경유, 두 가지를 필수로 한다.

**작업량**: 2-A는 워커 `screenshot()` + 결과 응답 필드 + 모달 렌더 — **드라이버 계약의 `screenshot()` 하나로 웹·Android·iOS가 동시에 해결된다**(§9-1). 2-B는 워커 Dockerfile에 `xvfb`/`x11vnc`/`novnc`/`websockify` + 기동 스크립트 + 토큰 검증 프록시 + 프론트 iframe. **모두 수요일 데모 범위 밖이며, 데모 이후 작업한다.**

#### 9-5-1. 백그라운드는 가역이다 — 컨펌창을 두지 않는다

초안에는 *"백그라운드 전환 시 수행중인 화면은 다시 볼 수 없습니다. 정말 끄시겠습니까?"* 컨펌이 있었으나 **삭제한다.**

§9-4 설계에서 워커는 **항상 화면을 그리고 있다**(2-A는 계속 캡처, 2-B는 항상 headed). 백그라운드는 "사용자가 안 보는 상태"일 뿐이므로 **언제든 되돌릴 수 있다.**

비가역이 되는 경로는 두 가지뿐이고, 둘 다 **실행 중 전환이 아니라 기동 시점의 선택**이다:

| 방식 | 왜 비가역인가 | 얻는 것 |
|------|---------------|---------|
| Playwright `launch({headless:true})` | launch 시점 고정 — 바꾸려면 브라우저 재시작 = TC 상태 소실 | 리소스 절약뿐 |
| `emulator -no-window` | 창 **없이 기동**. 실행 중 창 생성 불가 | 리소스 절약뿐 |

**되돌릴 수 있는 동작에는 확인창을 두지 않는다.** 확인창이 필요하다고 느껴지면 그건 설계가 비가역이라는 신호이고, 비가역일 이유가 없다면 확인창이 아니라 설계를 고쳐야 한다. 비가역의 유일한 대가가 리소스 절약인데, 사용자가 "지금 끄면 다시 못 보는데 괜찮나" 하고 망설이는 비용이 그보다 크다.

> **리소스 절약형 "조용히 실행"이 나중에 필요해지면** 4번(실행 중 토글)이 아니라 **2번(실행 시작 선택)에 옵션으로 붙인다** — `HEADLESS=true` / `emulator -no-window`로 기동. 그러면 그때도 컨펌창은 필요 없다.

#### 9-5-2. 중지는 비가역이다 — 컨펌창은 여기 붙는다

`recordResult`가 job의 RUNNING 상태를 요구하므로(`AgentExecutionServiceImpl:125-127`), 중지 시점에 **이미 실행에 들어간 TC의 결과는 기록되지 않는다**(2차 리뷰 N-2). 이건 진짜 되돌릴 수 없는 손실이라 확인이 필요하다.

```
실행을 중지합니다.
진행 중인 TC의 결과는 기록되지 않습니다.
                              [취소]  [중지]
```

구현은 Step 1-K와 동일하다(워커 상태 폴링 + 전용 `CancelledError` 분기 + `POST /{jobId}/cancel`). **패스오더처럼 결제가 걸린 상용 앱을 돌릴 때는 백그라운드보다 중지가 더 중요한 버튼**이므로, 두 버튼을 같은 줄에 두되 중지를 시각적으로 구분한다(§0-1 안전 규칙).

#### 9-5-3. "수행 중인 TC" 표시 — 다건은 백엔드 필드가 필요하다 ⚠️

| | 현 상태 | 필요 작업 |
|---|---|---|
| **단건** (`AgentRunModal`) | 모달이 `testCase.title`을 이미 갖고 있다 | **없음 — 지금도 표시 가능** |
| **다건** (`BatchAgentRunModal`) | `실행 중… {done}/{total}` 카운터만 (`:168`) | **백엔드 추가 필요** |

`JobResponse`에 **`currentTestCaseId`가 없다**(`AgentExecutionDto.java:32-48`). 완료된 TC는 결과 목록에 뜨지만 **지금 돌고 있는 TC가 무엇인지는 알 수 없다.** "3/7"까지가 한계다.

→ `AgentExecutionJobEntity`에 `current_test_case_id`를 추가하고 워커가 TC 시작 시 갱신한다(Step 7-B). 요구 ②의 "어떤 TC가 수행중인지 보인다"는 이게 없으면 **다건에서 성립하지 않는다.**

#### 9-5-4. 실행 대상 선택 — "매번 자유 선택"이 아니다

실행 대상 하나를 특정하려면 §9-2의 필드가 전부 필요하다(`exec_app_id`, `exec_device_name`, `exec_driver_url` …). 매 실행마다 이걸 입력할 수는 없으므로, **선택은 "저장된 프로파일 중 고르기"**여야 한다.

```
Product "패스오더"
  ├ 대상 1: ANDROID  (Pixel_7_API_34, com.paytalab.passorder)
  └ 대상 2: IOS      (iPhone 실기기, 번들 ID …)

Product "my-atlas"
  └ 대상 1: WEB      (http://localhost:5173)      ← 1개뿐 → 선택 단계 생략
```

- 등록된 대상이 **2개 이상**이면 2번 단계를 띄운다
- **1개면 건너뛴다** — my-atlas 자기 테스트는 지금과 동일한 경험을 유지한다
- 등록되지 않은 대상은 애초에 고를 수 없으므로 **"iOS 앱이 없는 제품에 iOS 실행"** 같은 사고가 원천 차단된다

> ⚠️ **§9-2 스키마에 영향이 있다.** 이 구조는 실행 대상이 **Product당 1개가 아니라 N개**임을 뜻한다. `product` 테이블에 `exec_*` 컬럼을 늘리는 방식으로는 표현할 수 없으므로 **`product_exec_target` 자식 테이블**로 가는 편이 자연스럽다. Phase 3 착수 시 확정한다(§12-5).

  ```js
  await driver.updateSettings({
    animationCoolOffTimeout: 0,        // 기본 2초
    snapshotMaxDepth: 20,              // 기본 50 — 조회 시간·토큰 동시 절감 (§8과 연결)
  });
  ```

### 🎯 수요일 데모 최소선

**목표 = iOS.** `Step 0-0 → (Xcode 대기 중 Android 트랙 0-A1~0-A3) → 0-I1 → 0-I1.5 → 0-I2 → 0-I3 → 게이트 0-C2 → Phase 1(1-K, 1, 2, 3)`. 여기까지면 데모가 성립한다.

**Android 트랙을 먼저 도는 것은 iOS를 미루는 게 아니다** — Xcode 설치 대기시간에 매핑 스크립트·프롬프트를 검증해두고 폴백을 확보하는 것이다(§0-1). Xcode가 준비되면 즉시 iOS로 넘어가고, iOS가 붙으면 **그것이 데모다.** 둘 다 되면 "같은 엔진으로 두 플랫폼"이 되어 임팩트가 가장 크다.

기존 `[AI 시험 실행]`(단건) 버튼 → Job 생성(SINGLE dry run) → 워커가 context를 받아 실행하는 경로가 이미 있으므로, **워커가 브라우저 대신 iPhone을 구동하기만 하면** `AgentRunModal`의 step별 판정 증적까지 그대로 뜬다.

- **`0-C2`(결정성 3/3)를 반드시 포함한다.** 이전 판은 데모 최소선에서 이 게이트를 빠뜨렸다 — 라이브 데모를 지키려고 만든 안전장치가 정작 실행 경로 밖에 있었다(3차 리뷰 M-2). **iOS에서는 시작 상태 고정이 수동이라 이 단계가 Android보다 비싸다**(Step 0-I1.5) — 시간을 따로 잡아둘 것
- **`0-I2`(대기·깊이 캡)를 건너뛰지 않는다.** 기본값이면 화면 확인마다 10~12초가 나가 데모 시간이 무너진다(리뷰 B-3)
- **백엔드는 무변경, 프론트는 [중지] 버튼 1개, 워커는 상태 폴링 + `CancelledError` 분기**다(Step 1-K). 당초 "한 줄도 안 고쳐도 된다"고 썼으나 상용 결제 앱을 멈출 수단 없이 돌릴 수는 없어 이것만은 예외로 둔다(리뷰 B-2)
- 대상 지정은 스키마 변경 없이 **워커 env로 하드코딩** (실행 프로파일 마이그레이션·대상 선택 UI는 Phase 3)
- 화면 중계는 **QuickTime USB 미러링**으로 대체한다(Android로 가면 에뮬레이터 창 그대로). §9-5의 3·4번(웹 UI 안 실시간 뷰 + 백그라운드 토글)은 **Phase 2이므로 데모 범위 밖**이다
- 워커는 **모바일 1종만 띄운다** (웹 워커 동시 기동 금지 — Step 6 미완 상태의 회피책)
- **남는 리스크는 WDA 서명 하나로 좁혀졌다** — 실기기는 확보됐고(User 확인) Xcode는 시간문제다. 그다음이 패스오더 프레임워크(Flutter 여부, Step 0-I3). 폴백 발동 시각은 **화요일 22시**(Step 0-I1)

> **⏱ 시간이 부족하면 Step 1을 데모 범위에서 뺄 수 있다** (3차 리뷰 M-4 — User 판단 필요).

## 13. 빠른 승리 — 모바일 웹은 지금도 거의 된다

대상이 **반응형 웹/PWA**라면 네이티브 드라이버가 전혀 필요 없다. Playwright의 디바이스 에뮬레이션만 켜면 된다.

```js
// index.js:75-76 — 현재
browser = await chromium.launch({ headless: cfg.headless });
const page = await browser.newContext().then((c) => c.newPage());

// 변경안 — 실행 프로파일에 exec_target_kind=MOBILE_WEB + 디바이스 프리셋
import { devices } from 'playwright';
const ctxOpts = ctx.execTarget?.kind === 'MOBILE_WEB'
  ? devices[ctx.execTarget.deviceName ?? 'iPhone 13']   // viewport + UA + touch + DPR
  : {};
const page = await browser.newContext(ctxOpts).then((c) => c.newPage());
```

**필요 작업**: 마이그레이션 1개(`exec_target_kind`, `exec_device_name`) + `WorkerContextResponse` 필드 2개 + 워커 3줄 + `ExecProfileModal` 셀렉트 1개. **스냅샷·액션·판정·프롬프트 전부 무변경.**

**한계**: 이것은 "앱"이 아니라 "모바일 화면의 웹"이다. 터치 이벤트와 반응형 레이아웃은 검증되지만, 네이티브 위젯·푸시·권한 팝업·앱 생명주기는 검증 대상이 아니다. 대상 제품이 진짜 네이티브 앱이라면 §10 경로가 필요하다.

**패스오더 실화면 검증**: 권한 팝업 화면(28노드)에서 조작 가능한 요소를 **정확히 1건** 추출했다.

```json
{"ref":"a0","role":"viewgroup","name":"확인","tag":"android.view.ViewGroup",
 "value":"","testId":"com.paytalab.mkseo.passorder:id/btn_ok","clickable":true,"enabled":true}
```

- 이름이 컨테이너에 없고 자식에 있었으나 `descendantText()`가 `"확인"`으로 복원
- locator는 **안정적인 `resource-id`**(`btn_ok`)로 잡힘 — xpath 폴백 불필요
- **기존 웹 프롬프트가 소비하는 것과 동일한 스키마**로 나옴 → §0의 핵심 가설 실증

기본 앱(런처) 트리로도 §4 매핑표를 검증했다. **표의 속성이 전부 실재**한다 — `class` / `text` / `content-desc` / `resource-id` / `clickable` / `enabled` / `displayed` / `scrollable` / `bounds`.

> ⚠️ **새 발견 — 덤프 경로에 따라 포맷이 다르다.** raw `adb shell uiautomator dump`에는 **`displayed` 속성이 없고**, Appium `getPageSource`에는 있다. `displayed`를 필수로 읽으면 raw 덤프에서 **후보가 0건**이 된다(실제로 겪음). → 매핑 로직은 `displayed` 부재 시 **`bounds` 면적으로 폴백**해야 두 경로 모두에서 동작한다. Phase 1 Step 2에 반영.

**실측 (§8의 1순위 측정 항목 — 추정치를 대체)**

| 항목 | 추정(§8) | **실측** |

| `getPageSource` 지연 | "수백 ms ~ 수 초" | **123 / 165 / 250 ms** — 추정보다 훨씬 빠름 |
| 세션 생성 | — | 10.3초 (job당 1회, step당 아님) |

**locator 분포** — `resource-id` 7 / `accessibility id` 8 / **`xpath` 1**
→ §4-1이 우려한 "xpath 취약성"은 **소수 케이스**다. 대부분 안정적인 id/접근성 id로 잡힌다.

**새 발견 — 웹과 반대 방향의 이름 문제**
웹의 B2-5는 "컨테이너 이름에 자식 버튼 텍스트가 다 섞임"이었는데, 네이티브는 **반대**다: 클릭 가능한 컨테이너의 `text`가 비어 있고 라벨이 자식 `TextView`에 있다. → 매핑 스크립트에 `descendantText()`를 두어 자기 텍스트가 없으면 자손 텍스트를 모으되, **자식이 그 자체로 clickable이면 제외**해 대상이 섞이지 않게 했다.

**새 발견 — 중복 후보**
부모 `ViewGroup`(clickable)과 자식 `TextView`(clickable)가 **같은 대상을 두 번** 올린다(`"Mon, Aug 24"` 2건). 웹 B2-7의 cursor 상속 중복과 같은 구조의 문제이며, 동일한 해법(조상이 이미 후보면 자손 제외, 단 역할이 다르면 유지)이 필요하다. → Phase 1 Step 2에서 반영.

> ⚠️ **§4-1의 xpath 취약성 우려가 실제 화면에서 현실화됐다.** 초기 소형 화면에서는 xpath가 1/16에 불과해 "소수 케이스"로 판단했으나, **실제 콘텐츠 화면에서는 20/37**이다. `resource-id`가 없는 동적 리스트 항목이 많기 때문이다. → Phase 1 Step 2의 **name/testId 폴백 재조회**는 선택이 아니라 **필수**다.

**🆕 세 번째 이름 패턴 — 라벨이 형제 노드에 있다 (중대 발견)**

지금까지 파악한 이름 패턴이 둘이었는데(웹 B2-5의 "자식 텍스트 혼입", 네이티브의 "라벨이 자식에"), **세 번째가 있다**:

```
clickable=false  content-desc="재주문"   View   ← 라벨
clickable=true   (텍스트 없음)           View   ← 클릭 대상 (형제!)
```

라벨이 **자식도 조상도 아닌 형제**다. 보이지 않는 clickable View가 라벨 View 위에 겹쳐 있는 오버레이 패턴이라 **트리 탐색으로는 영원히 못 찾는다.**

→ **해법: 화면 좌표(bounds) 겹침으로 라벨을 찾는다.** 라벨 박스의 80% 이상이 후보 박스 안에 들어오면 그 후보의 이름으로 채택(단 4개 초과로 겹치면 화면 전체를 덮는 컨테이너이므로 제외).

**효과: 이름 있는 후보 4/37 → 28/37.** 이 처리가 없으면 `재주문`·`쿠폰함`·`포인트/스탬프`·`사다리타기`·`경유매장찾기`·`선물하기`가 **전부 무명**으로 나와 에이전트가 지목할 수 없다. Phase 1 Step 2 필수 반영.

**스크롤 컨테이너 이름 오염**: `RecyclerView`/`ScrollView`에 자손 텍스트를 모으면 화면의 모든 글자가 이름 하나로 뭉친다(`"HOT 여름 취향전 컵빙수 EVENT 상생할인..."`). → `scrollable && !clickable`이면 자손 텍스트 수집을 건너뛴다.

> 🛒 **안전 관련 실측**: 이 계정의 **장바구니에 이미 상품이 담겨 있다**(`파리바게뜨 방이시장점 / 초코 마카롱 1`). 읽기 전용 TC가 결제 화면 근처로 가면 **실제 주문으로 이어질 수 있는 상태**다. §0-1 안전 규칙(장바구니 이후 단계 금지)을 반드시 지킬 것.

| 디스크 | **~3.9 GB / 개** |
| 개수 제한 | 없음 (디스크 한도 내). 현재 여유 78.5GB → 10여 개 여유 |

**Quick Boot과 구분할 것** — `fastboot.forceFastBoot=yes`의 Quick Boot은 **종료할 때마다 자동으로 덮어써지므로** 0-C2의 3회 반복에 쓸 수 없다(회차마다 직전 회차의 흔적에서 출발). 명시적 스냅샷만이 반복 가능한 시작점이다.

**시작 상태 3종 운용안** — 앞서 "권한 TC는 시작 상태가 다르다"고 남긴 문제(아래 항목 ③)의 해법이다:

| 스냅샷 | 상태 | 용도 |
|--------|------|------|
| `fresh-perms` | 권한 미처리 | **권한 TC 전용** |
| `pre-login` | 온보딩·권한 정리 완료, 로그인 직전 ✅ **생성됨** | 로그인 플로우 TC |
| `base` | 로그인 완료 + 홈 | 일반 TC 기본 시작점 |

> ⚠️ **한계 — 서버 상태는 롤백되지 않는다 (중요).** 스냅샷은 **기기만** 복원한다. TC가 실행 중 패스오더 **서버**에 만든 것(주문·장바구니·계정 설정)은 스냅샷을 되돌려도 **그대로 남는다.** 화면만 과거로 가고 데이터는 안 간다.
> 읽기 전용 TC만 돌리는 현 계획에서는 무해하지만, 쓰기 동작을 테스트하게 되면 **스냅샷이 테스트 격리를 보장한다고 착각해서는 안 된다.** 서버 측 정리는 별도 수단(테스트 계정 분리, API 정리)이 필요하다.
>
> 부수 한계: ① **세션 토큰 만료** — 며칠 지난 스냅샷은 복원해도 로그아웃 상태일 수 있다. ② 에뮬레이터·시스템 이미지 업그레이드 시 스냅샷 무효화.

### ⚠️ 시스템 권한 다이얼로그도 TC 대상이다 (User 지적, 2026-08-24) — Phase 1 필수 반영

권한 요청 화면을 "셋업 잡음"으로 치우면 안 된다. **"알림 권한을 거부하면 X가 표시된다", "위치 권한을 허용하면 내 주변 매장이 뜬다"는 정당한 TC**이며, 자동화가 이걸 실행할 수 있어야 한다.

**실측 — 매핑은 이미 통과한다** (패스오더 위치 권한 다이얼로그, 7,252자 → 후보 7건, 전부 `resource-id` locator)

| 요소 | testId |
|------|--------|
| While using the app | `com.android.permissioncontroller:id/permission_allow_foreground_only_button` |
| Only this time | `...:id/permission_allow_one_time_button` |
| Don't allow | `...:id/permission_deny_button` |
| Precise / Approximate | `...:id/permission_location_accuracy_radio_fine` / `_coarse` |

**그러나 설계에 함정이 3개 있다:**

1. **패키지 필터를 걸면 안 된다 (치명적)** — 권한 다이얼로그는 대상 앱이 아니라 **`com.android.permissioncontroller`** 패키지에 있다. 스냅샷을 `appPackage` 기준으로 제한하면 **다이얼로그가 통째로 안 보이고**, 에이전트는 "화면에 아무것도 없다"며 실패한다. → `drivers/mobile.js`의 스냅샷은 **현재 포커스 윈도우 전체**를 대상으로 하고, 패키지 필터를 두지 않는다.

2. **`appium:autoGrantPermissions`를 켜면 안 된다** — 켜면 권한이 자동 허용되어 **다이얼로그가 아예 뜨지 않는다.** 검증하려는 대상 자체가 사라지므로 편의 옵션이 TC를 무력화한다. 기본 **false**를 유지하고, 필요한 TC에서만 켜도록 **실행 프로파일 옵션**으로 노출한다. (iOS도 동일 — `appium:autoAcceptAlerts` / `autoDismissAlerts`를 꺼야 한다)

3. **권한 TC는 시작 상태가 다르다** — 권한은 한 번 허용/거부하면 **다시 묻지 않는다.** 그런데 Step 0-A1.5의 AVD 스냅샷은 "권한 처리가 끝난" 상태를 고정한다. 즉 **스냅샷 하나로는 권한 TC를 반복 실행할 수 없다.**
   → 시작 상태를 **2종**으로 관리한다: ① 권한 처리 완료 + 로그인 상태(일반 TC용) ② 권한 미처리 상태(권한 TC용). 또는 TC 전처리로 `adb shell pm reset-permissions` / `pm revoke <pkg> <permission>`을 수행해 되돌린다. 후자가 스냅샷 2벌보다 가볍다.

> 이 세 가지는 §9-1 Driver 계약과 §10 Phase 1 Step 2에 반영해야 한다. 특히 1번은 **기본값으로 패키지 필터를 넣기 쉬운 자리**라 명시적으로 금지해 둔다.

#### 🛑 TC-2 실패의 진짜 원인 — 엔진이 Segment Path를 버리고 있다 (User 지적으로 정정)

> **이 문서의 이전 판은 "TC-2에 전제조건 step이 빠졌다 = TC 결함"으로 결론냈으나 틀렸다.** TC-2(`tc-id 3412`)는 **정상적으로 작성된 TC**다. 전제조건은 step이 아니라 **Segment Path**에 들어 있다.

Registry의 정보 구조에서 TC의 위치 자체가 전제조건을 선언한다:

```
검색창  →  검색 전 화면  →  나와 가까운 매장 목록
                                    └─ [TC 3412] 목록의 매장 터치 시, 매장 상세 페이지 진입
```

즉 이 TC의 전제조건은 **"나와 가까운 매장 목록이 출력된 상태"**이며, 작성자는 그것을 path로 명시해 두었다. step에 중복해 적지 않는 것이 이 레포의 컨벤션이다.

**그런데 엔진이 그 정보를 워커에 전달하지 않는다:**

```java
// AgentExecutionDto.java:104-108 — path가 빠져 있다
return new TestCaseContext(
        e.getId(), e.getTitle(), e.getPreconditions(),
        e.getSteps(), e.getExpectedResults());
```

`TestCaseEntity:29`에 `Long[] path`(segment ID 배열)가 엄연히 존재하는데 **컨텍스트에서 통째로 누락**된다. 에이전트는 자기가 어디서 시작해야 하는지 모른 채 "앱이 마침 떠 있는 화면"에서 실행을 시작한다. TC-2가 홈(지도 탭)에서 시작해 RecyclerView만 5회 클릭한 것은 **당연한 결과**다.

TC-4(전제조건 step을 수동으로 붙인 대조군)가 PASS한 것은, **path가 했어야 할 일을 내가 손으로 대신했기 때문**이다:
- 검색창 → `StoreSearchActivity` → 매장 목록 노출
- 에이전트가 `"최상단 매장"`을 정확히 해석해 **`우지커피 석촌역점`** 클릭
- 판정기가 매장명·주소(`서울특별시 송파구 백제고분로41길 11`)·평점·영업시간으로 상세 진입 확인

**→ Phase 1 필수 수정 (2건)**

1. **`TestCaseContext`에 segment path를 이름으로 해석해 포함한다.** ID 배열(`[812, 815, 823]`)은 LLM에게 무의미하므로 **세그먼트 이름 배열**(`["검색창","검색 전 화면","나와 가까운 매장 목록"]`)로 변환해 실어야 한다.
2. **워커가 path를 전제조건 네비게이션 목표로 삼아 TC step 실행 전에 그 상태에 도달한다.** 이는 v20의 `agenticGoal(seedNote)`(`agent.js:278`)이 이미 하던 역할과 **정확히 같은 자리**다 — Product 단위 고정 문구였던 seed를 **TC 단위 path**로 대체·확장하면 된다.

> 이 발견은 §0-1에서 정리한 "시작 상태" 논의(권한·로그인·위치)의 **네 번째 축**이다. 앞의 셋은 기기/계정 상태였고, 이것은 **앱 내 화면 위치**다. 스냅샷으로는 해결되지 않으며(TC마다 시작 화면이 다르다) 반드시 실행 시 네비게이션으로 도달해야 한다.

#### 🆕 액션 어휘 부족 — 키 입력이 없다 (TC-3 실패 원인)

TC-3 step1은 `fill` 수정 후 **PASS**했다. 그러나 step2~5는 전부 실패했는데, 원인은 **검색이 제출되지 않았기 때문**이다.

수동 실측으로 확정: `adb shell input keyevent 66`(ENTER)을 보내니 `'starbucks'에 관한 검색 결과가 없어요`가 떴다 — **엔터가 있어야 검색이 실행되고, 그래야 최근 검색어에 저장된다.**

현재 어휘는 `click | fill | select | navigate | done`(§5)뿐이라 **키를 보낼 방법이 없다.** 웹에서는 폼이 자동 제출되거나 버튼이 DOM에 있어서 드러나지 않던 결함이다.

→ **Phase 1에서 `key` 액션 추가 필수**: `Enter` / `Search`(IME action) / `Back`. §5의 신규 액션 표에 `back`·`scroll`은 있었으나 **키 입력이 누락**되어 있었다.

#### 🐛 엔진 버그 2건 (발견·수정)

### 🆕 시작 상태의 세 번째 축 — 위치 (User 지적)

**프로모션 모달이 12개 연속으로 뜬다** — 로그인 후 홈 진입 시 캐러셀형 프로모션이 연달아 표시된다(페이지 인디케이터 12개). `일주일 동안 보지 않기` 체크박스를 **체크한 뒤 `닫기`**를 눌러야 일괄 해소된다(체크박스만 누르면 안 닫힘). 시작 상태 고정 시 반드시 정리해야 한다.

**확보한 스냅샷 3종** (각 ~3.8GB)

| 스냅샷 | 권한 | 로그인 | 위치 | 프로모션 |
|--------|:---:|:---:|:---:|:---:|
| `pre-login` | 처리됨 | ✗ | ✗ | — |
| `base` | 처리됨 | ✓ | ✗ (마운틴뷰) | 미정리 |
| **`base-located`** | 처리됨 | ✓ | ✓ **송파구** | 정리됨 |

### 미완 — User 대기

| Step | 상태 | 막힌 이유 |
|------|------|-----------|
| 0-0a Xcode | ⏳ | Apple ID 인증 필요 — **User 실행**. iOS 트랙(0-I*) 전체가 여기 종속 |
| 0-A1.5 AVD 스냅샷 | ⏳ | 패스오더 **로그인**이 User 실행 (카카오/Apple/이메일). 팝업·권한 정리는 **완료**, 로그인 화면까지 도달해 둠 |
| 0-A3 gold TC | ⏳ | 0-A1.5 선행 (로그인된 상태에서 시작해야 함) |
| 0-I1~0-I3 | ⏳ | Xcode 선행. **아이폰은 USB 연결 확인됨** |
| 0-C1~0-C3 | ⏳ | 위 선행 |

**Android 트랙 요약**: 최대 리스크 2건(Flutter · Play Integrity)이 **모두 해소**됐고, 남은 것은 User의 로그인뿐이다. 도구 체인·매핑·실측이 끝나 있으므로 로그인만 되면 0-A3로 바로 진입한다.
