## 무엇을 만드나

Figma와 PRD를 넣으면 **분석 보고서로 QA와 질의응답을 주고받은 뒤**, QA가 OK하면 TC를 만드는 Claude Code 스킬.
새 TC 생성만이 아니라 **기존 TC 수정안**까지 낸다.

- 가장 큰 고충: 사소한 UI가 바뀔 때마다 기존 TC를 찾아 고치는 일
- 가장 시간이 드는 일: PRD·Figma를 읽고, 이전 정책과 충돌하는지 확인하며 TC를 쓰는 일

## 흐름

```
Figma + PRD 링크 입력
  → 분석 → 분석 보고서 (1차)
  → QA 확인·답변 → 반영 → 분석 보고서 (2차)
  → ... 반복 ...
  → QA "OK"
  → TC 생성: 수정안(전/후) · 신규 · 폐기 후보
  → QA 최종 확인 → 시트에 반영
```

- QA가 OK하기 전에는 TC를 만들지 않는다.
- 결과 확인은 QA가 직접 한다. 자동 채점은 하지 않는다.

## 입력

| 무엇 | 어디서 |
|---|---|
| PRD, 이전 정책 | 사내 문서 MCP (검색 가능) |
| Figma | Figma MCP |
| 기존 TC | 구글 시트. ID가 없으므로 **대/중/소분류 + 제목**으로 TC를 구분한다 |

**바뀐 점 찾기:** 이전 Figma와 비교하지 않고 **지금 Figma와 기존 TC를 바로 비교**한다. TC에는 "다음", Figma에는 "계속"으로 되어 있으면 수정 대상이다.
**영향 TC 찾기:** Figma 화면 이름을 시트의 대/중/소분류와 맞춰서, 해당 분류의 TC만 본다.

## 스킬

[skills/tc-studio/](../../skills/tc-studio/) — 회사 정보 없이 범용으로 만든다.

| 파일 | 내용 |
|---|---|
| `SKILL.md` | 원칙, 절차(입력 → 분석 → 보고서 → 답변 반영 → TC 생성), TC 작성 규칙 |
| `templates/analysis-report.md` | 분석 보고서 양식 |
| `templates/tc-output.md` | TC 출력 양식: 수정안(전/후), 신규, 폐기 후보, 요구사항 커버 |

- 시트 열 구성은 스킬에 적지 않는다. 실행할 때 머리행을 읽어 그 순서에 맞춘다.
- 신규 TC는 CSV 파일로도 저장한다. 시트의 파일 → 가져오기로 넣는다.
- 자동화 툴용 JSON은 툴 형식을 확인한 뒤 추가한다.

## 범위 밖 (나중에)

- 개발 결과가 Figma와 다른지 확인 → 실제 앱 화면이 필요하므로 실행 단계에서
- my-atlas Test Studio 개선 → 스킬이 동작한 뒤 같은 방식으로 반영. my-atlas에는 사내 문서 MCP가 없으므로 정책 기록을 직접 쌓는 방식이 필요하다
- 참고: 현재 my-atlas는 기존 TC를 context로 넣지 않는다(v2.5에서 제거, 예시 TC만 넣음)
